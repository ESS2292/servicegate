Redis “Can’t handle RDB format version” after changing the image tag in Compose or CI

Redis saves its data to dump.rdb in the format of the version that wrote it. If a Compose file, a workflow, or a test then starts an older Redis on that file, the server exits on startup. Unlike Postgres, Redis has changed this format in minor releases too, and redis:latest now writes a format that every earlier tag rejects.

The error

Real output from starting redis:7.4 (Redis 7.4.12) on a named volume whose dump.rdb was written by redis:latest (Redis 8.12.0), run with Docker 26.1.5 on 24 November 2026. The container exits with status 1:

1:M 24 Nov 2026 16:17:56.660 * Server initialized
1:M 24 Nov 2026 16:17:56.660 # Can't handle RDB format version 17
1:M 24 Nov 2026 16:17:56.660 # Fatal error loading the DB, check server logs. Exiting.

The check is in the loader. In Redis 8.12.0, rdbLoadRioWithLoadingCtxInternal reads the 9-byte header (REDIS plus four digits) and rejects any file whose number is higher than its own RDB_VERSION:

rdbver = atoi(buf+5);
if (rdbver < 1 || rdbver > RDB_VERSION) {
    serverLog(LL_WARNING,"Can't handle RDB format version %d",rdbver);
    return C_ERR;
}

Newer servers read older files. Older servers refuse newer ones, and I found no setting to relax this: the 7.2.17, 7.4.12, and 8.12.0 redis.conf files have no RDB version-check option. Redis 6.2 prints a slightly different last line: Fatal error loading the DB: Invalid argument. Exiting.

Which Redis versions write which RDB format

RDB_VERSION from src/rdb.h at each release tag of redis/redis, checked on 24 November 2026. The header comment in rdb.h reads: “When the format changes in a way that is no longer backward compatible this number gets incremented.”

6.2.249REDIS0009
7.0.1510REDIS0010
7.2.1711REDIS0011 (seen on disk)

8.12.017REDIS0017 (seen on disk)

The 7.0 change is documented in the 7.0.0 release notes: “Redis 7 uses a new version 10 format for RDB files, which is incompatible with older versions.” The others are visible only in the source. Note the minor releases: 7.2 → 7.4, and every 8.x minor since 8.6, bumped the number. A file written by Redis 8.12 cannot be read by 8.10.

What the tags point to today

Pulled from Docker Hub on 24 November 2026 (linux/amd64). Versions are the image’s REDIS_VERSION. The tag list matches library/redis in docker-library/official-images.

So redis:8 is not a stable format pin. It moved from RDB 12 (8.0–8.4) to 17 (8.12) as the tag advanced. Any volume written by today’s redis:8 or latest fails on every older tag in the table.

Reproduced: forward works, backward fails

Each volume was written by one tag (SET, then SAVE) and then mounted at /data by another tag. This is the same layout as a Compose service with volumes: - redis-data:/data. Docker Compose itself was not installed on the test machine, so the containers were started with docker run and named volumes. Last log lines, verbatim:

Written by 8.12.0 (latest), started with redis:8.10:

1:M 24 Nov 2026 16:19:54.857 # Can't handle RDB format version 17
1:M 24 Nov 2026 16:19:54.857 # Fatal error loading the DB, check server logs. Exiting.

Written by 7.4.12, started with redis:7.2 (same major, different minor):

1:M 24 Nov 2026 16:18:07.284 # Can't handle RDB format version 12
1:M 24 Nov 2026 16:18:07.284 # Fatal error loading the DB, check server logs. Exiting.

Written by 7.2.17, started with redis:6.2:

1:M 24 Nov 2026 16:18:10.618 # Can't handle RDB format version 11
1:M 24 Nov 2026 16:18:10.618 # Fatal error loading the DB: Invalid argument. Exiting.

The same failure appeared for 8.12.0 files started with redis:7.2 and redis:6.2. In the other direction, a 7.2.17 file started with redis:latest, and a 7.4.12 file started with redis:8.4, both loaded (Done loading RDB, keys loaded: 1, keys expired: 0.). After the failed 7.4 start, the 8.12.0 volume still loaded in redis:latest and returned the key. The old server refuses the file but does not change it.

You do not need an explicit SAVE. With no config file, a plain docker stop of redis:latest wrote the file on shutdown:

$ docker run -d --name cache -v redis-data:/data redis:latest
$ docker exec cache redis-cli SET session:42 ok
OK
$ docker stop cache
1:M 24 Nov 2026 16:19:28.162 * Saving the final RDB snapshot before exiting.
1:M 24 Nov 2026 16:19:28.164 * DB saved on disk
1:M 24 Nov 2026 16:19:28.164 # Redis is now ready to exit, bye bye...
$ docker run --name cache -v redis-data:/data redis:7.2
1:M 24 Nov 2026 16:19:28.487 * Server initialized
1:M 24 Nov 2026 16:19:28.487 # Can't handle RDB format version 17
1:M 24 Nov 2026 16:19:28.487 # Fatal error loading the DB, check server logs. Exiting.

One image detail: the 7.2.17 image declares VOLUME /data, and the 8.12.0 image sets WORKDIR /data with no VOLUME line. docker image inspect agrees (Volumes={"/data":{}} for 7.2 and 6.2, null for latest). A Compose file that mounts a named volume at /data keeps the file in both cases, and that is the setup that hits this error.

Why CI stays green while local Compose breaks

GitHub’s service container docs say: “GitHub creates a fresh Docker container for each service configured in the workflow, and destroys the service container when the job completes.” A Redis service in CI starts with no dump.rdb, so any tag works there. The failure shows up on a developer machine whose Compose volume was written by a newer Redis. A common way to get there: Compose used redis:latest or redis:8, someone pins Compose to redis:7.2 “to match CI,” and the next docker compose up exits. It also happens when a dump.rdb copied from a newer server is loaded into an older test container.

Fix it

  1. Go back to a version at least as new as the writer. The file is untouched by the failed start, so restoring the newer tag brings the data back. You can check what wrote it: the first nine bytes of dump.rdb are the header (head -c 9 dump.rdb printed REDIS0017 for 8.12.0), and a successful load logs Loading RDB produced by version 8.12.0.
  2. If it is throwaway cache data, reset the volume. docker compose down -v removes “named volumes declared in the ‘volumes’ section of the Compose file and anonymous volumes attached to containers” (compose down reference). This deletes the data.
  3. Do not plan on downgrading a dump. The loader rejects any file newer than itself, as shown above. I did not find or test a supported way to convert an RDB file to an older format. Treat a newer dump.rdb as one-way.
  4. Pin to a minor, not a major, and use the same pin everywhere. Because 8.x minors change the format, redis:8.12 is a tighter pin than redis:8. Put it in Compose, the workflow services: block, Testcontainers, and REDIS_VERSION in .env.example, and change them all in one pull request.
# .env.example
REDIS_VERSION=8.12

# docker-compose.yml
services:
  cache:
    image: redis:${REDIS_VERSION:-8.12}
    ports:
      - "6379:6379"
    volumes:
      - redis-data:/data
volumes:
  redis-data:

# .github/workflows/ci.yml
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      redis:
        image: redis:8.12
        ports:
          - 6379:6379
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

# test/cache.test.js
import { RedisContainer } from "@testcontainers/redis";
const container = new RedisContainer("redis:8.12-alpine");

What ServiceGate does not detect

  • Minor drift does not fail the job. ServiceGate 0.1.0 reports a minor difference as a warning (exit 0). For Redis that is not enough: 8.12 vs 8.10, and 7.4 vs 7.2, are RDB format changes, as reproduced above. Read the warnings, or gate on --json output yourself.
  • A floating major is not compared with a minor. Compose redis:8 and workflow redis:8.10 got OK — Compose, CI, and test service images agree. (exit 0) in a test run. Today redis:8 is 8.12.0, which writes RDB 17, and 8.10 cannot read it.
  • It does not look at volumes or dump.rdb. It reads tags in committed files. It cannot see which Redis wrote a developer’s local volume, so it cannot predict this error on a given machine.
  • It does not resolve tags. It flags latest and a missing tag as unpinned. It does not know that latest and 8 mean 8.12.0 today, or which RDB version a tag writes.
  • AOF was not tested. This guide only covers RDB snapshots. Setups with appendonly yes were not reproduced here.
