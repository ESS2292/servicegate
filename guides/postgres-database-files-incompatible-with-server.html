Postgres “database files are incompatible with server” after a major version change in Compose or CI

A Postgres data directory belongs to one major version. When a Compose file, a workflow, or postgres:latest moves to a different major while an old volume is still attached, the server refuses to start. CI rarely notices, because service containers start empty for each job.

The error

This is the real output from starting the PostgreSQL 17.12 server on a data directory created by PostgreSQL 16.16 (run on 22 November 2026; how it was run is explained below):

FATAL:  database files are incompatible with server
DETAIL:  The data directory was initialized by PostgreSQL version 16, which is not compatible with this version 17.12 (Debian 17.12-1.pgdg13+1).

The PostgreSQL docs on upgrading a cluster explain why: “Minor releases never change the internal storage format and are always compatible with earlier and later minor releases of the same major version number.” For major releases, “the internal data storage format is subject to change,” so moving data needs a dump and restore, pg_upgrade, or replication. The same page notes that checks prevent a data directory from being used with an incompatible version, “so no great harm can be done by trying to start the wrong server version.” The server stops; it does not corrupt the volume.

What the tags point to today

Checked on 22 November 2026 through the Docker Hub registry API (linux/amd64 image config of the official postgres image):

TagPG_VERSIONPGDATA / VOLUME
postgres, postgres:latest, postgres:1919.0-1.pgdg13+1/var/lib/postgresql/19/docker / /var/lib/postgresql
postgres:18, postgres:18.718.7-1.pgdg13+5/var/lib/postgresql/18/docker / /var/lib/postgresql
postgres:17, postgres:17.1217.12-1.pgdg13+1/var/lib/postgresql/data / /var/lib/postgresql/data
postgres:16, postgres:16.1616.16-1.pgdg13+1/var/lib/postgresql/data / /var/lib/postgresql/data

Two consequences. First, any Compose file or workflow that uses postgres or postgres:latest is now on PostgreSQL 19. A local volume that an earlier latest initialized (18, for example) will not start on it. Second, PostgreSQL 18 changed where the image keeps its data, which matters for Compose files written for 17 and earlier.

Reproduced: upgrade, latest, and downgrade

The test machine had no Docker. Instead, I ran the same server packages the official image installs. The image’s Dockerfile installs postgresql-$PG_MAJOR from apt.postgresql.org (trixie-pgdg). The 16.16-1.pgdg13+1, 17.12-1.pgdg13+1, and 18.7-1.pgdg13+5 packages match the image PG_VERSION values above exactly. For 19, the package was 19.0-2.pgdg13+1, while the image has 19.0-1.pgdg13+1. Each data directory was created with that major’s initdb, then started with another major’s postgres binary. Timestamps are removed below; nothing else is changed.

Data from 16, server 18:

FATAL:  database files are incompatible with server
DETAIL:  The data directory was initialized by PostgreSQL version 16, which is not compatible with this version 18.7 (Debian 18.7-1.pgdg13+5).

Data from 18, server 19 (an old latest volume meeting today’s latest):

FATAL:  database files are incompatible with server
DETAIL:  The data directory was initialized by PostgreSQL version 18, which is not compatible with this version 19.0 (Debian 19.0-2.pgdg13+1).

Going back: data from 18, server 16 or 17. Rolling a tag back fails even earlier. The postgresql.conf that 18’s initdb wrote contains a setting the older servers do not recognize:

LOG:  unrecognized configuration parameter "autovacuum_worker_slots" in file "/tmp/pgtest/d18/postgresql.conf" line 687
FATAL:  configuration file "/tmp/pgtest/d18/postgresql.conf" contains errors

With that file emptied, PostgreSQL 16 reports the same version check as above: The data directory was initialized by PostgreSQL version 18, which is not compatible with this version 16.16 (Debian 16.16-1.pgdg13+1). Downgrading a volume is a restore from a dump, not a tag edit.

In the official image, the entrypoint skips initdb when $PGDATA/PG_VERSION already exists and starts the server (docker-entrypoint.sh). That is where the server’s own version check produces the FATAL lines above.

The PostgreSQL 18+ image refuses old /var/lib/postgresql/data volumes

The Docker Hub PGDATA notes say the variable “was changed to be version specific in PostgreSQL 18 and above” (/var/lib/postgresql/18/docker), and that “the defined VOLUME was changed in 18 and above to /var/lib/postgresql.” The registry check above confirms this for 18 and 19.

Most Compose files written for 17 and earlier mount pgdata:/var/lib/postgresql/data. After a bump to postgres:18, postgres:19, or latest, the 18+ entrypoint looks for a PG_VERSION file in /var/lib/postgresql, /var/lib/postgresql/data, and /var/lib/postgresql/*/docker. It also checks for a bare mount at /var/lib/postgresql/data. If it finds either, it exits with status 1 and prints a message that starts:

Error: in 18+, these Docker images are configured to store database data in a
       format which is compatible with "pg_ctlcluster" (specifically, using
       major-version-specific directory names).  This better reflects how
       PostgreSQL itself works, and how upgrades are to be performed.

It then lists the old data location and says this is “usually the result of upgrading the Docker image without upgrading the underlying database using ‘pg_upgrade’,” pointing to docker-library/postgres issue #37. That text is quoted from the entrypoint source at the linked commit. I did not run it in a container for this guide.

Why CI stays green while local Compose breaks

GitHub’s service container docs say: “GitHub creates a fresh Docker container for each service configured in the workflow, and destroys the service container when the job completes.” A workflow that moves to postgres:18 runs initdb on an empty directory every time and passes. The developer whose Compose volume was initialized by 16 is the one who hits the FATAL line. The reverse also happens: Compose moves forward, CI stays behind, and tests pass against a server nobody runs locally. Either way, the two files disagree and nothing fails the pull request that caused it.

Fix it

  1. Pin a major everywhere. Use postgres:18 (or 18-alpine) in Compose, the workflow services: block, Testcontainers, any database Dockerfile, and POSTGRES_VERSION in .env.example. A major tag still takes minor releases, which the docs say are storage-compatible.
  2. If the local data matters, move it. Start the old major again, run pg_dumpall, start the new major on an empty volume, and restore with psql. The upgrade docs recommend the newer version’s dump tools. pg_upgrade is faster but needs both majors’ binaries side by side.
  3. If it is throwaway dev data, reset the volume. docker compose down -v removes named volumes declared in the Compose file (compose down reference). This deletes the data.
  4. On 18+, mount /var/lib/postgresql, not /var/lib/postgresql/data. Use a new, empty volume, or move the old files into a PG_MAJOR/docker subdirectory, as the Docker Hub notes describe.
  5. Change every file in one pull request.
# .env.example
POSTGRES_VERSION=18

# docker-compose.yml
services:
  db:
    image: postgres:${POSTGRES_VERSION:-18}
    environment:
      POSTGRES_PASSWORD: postgres
    volumes:
      - pgdata:/var/lib/postgresql
volumes:
  pgdata:

# .github/workflows/ci.yml
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:18
        env:
          POSTGRES_PASSWORD: postgres
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

# test/db.test.js
import { PostgreSqlContainer } from "@testcontainers/postgresql";
const container = new PostgreSqlContainer("postgres:18-alpine");

Unpinned images are warnings (errors with --strict-pins). postgres in Compose and postgres:latest in CI. Exit code 0 by default:

  [unpinned-image] Postgres image is unpinned (latest) at docker-compose.yml:3 (compose). Pin a numeric major tag instead of 'latest'.

OK — Compose, CI, and test service images agree.

What ServiceGate does not detect

  • It does not look at volumes. ServiceGate reads tags in committed files. It cannot see which major initialized a developer’s local volume, so it cannot predict the FATAL error on a given machine. It only keeps the files in agreement, which stops the drift that leads to it.
  • It does not check mount paths or PGDATA. A repository with postgres:18 in Compose and CI, but the volume still mounted at /var/lib/postgresql/data, gets OK — Compose, CI, and test service images agree. (exit 0) in a test run. The 18+ entrypoint error above is not caught.
  • It does not resolve latest. It flags the tag as unpinned. It does not know that latest means 19 today.
  • Destructured CommonJS requires are missed in 0.1.0. In a test run, const { PostgreSqlContainer } = require("@testcontainers/postgresql") was not recognized as a Testcontainers file. The postgres:17-alpine literal was skipped, and only 3 pins were counted. ES import and const tc = require(...) were detected.
  • Minor versions agree by design. postgres:18 and postgres:18.7-alpine count as the same major. That matches Postgres storage compatibility, but extension or behaviour changes inside a major are out of scope.
