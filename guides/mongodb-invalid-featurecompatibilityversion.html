MongoDB “UPGRADE PROBLEM: Found an invalid featureCompatibilityVersion” after changing the mongo image tag

A MongoDB data directory records a feature compatibility version (FCV). Each mongod only opens a short list of FCVs. Change the mongo tag in Compose by more than one step, or move it backwards, and the server exits on startup with exit code 62. mongo:latest is now MongoDB 9.0.8, and mongo:8 is 8.3.17, so both tags can trigger this.

The error

Real output from starting mongo:8.0 (MongoDB 8.0.38) on a named volume mounted at /data/db whose data was written by mongo:6.0 (6.0.28). Run with Docker 26.1.5 on 26 November 2026. The container exits with status 62. This is the one "s":"F" (fatal) line, verbatim:

{"t":{"$date":"2026-11-26T16:19:31.065+00:00"},"s":"F",  "c":"CONTROL",  "id":20573,   "ctx":"initandlisten","msg":"Wrong mongod version","attr":{"error":"UPGRADE PROBLEM: Found an invalid featureCompatibilityVersion document (ERROR: Location4926900: Invalid featureCompatibilityVersion document in admin.system.version: { _id: \"featureCompatibilityVersion\", version: \"6.0\" }. See https://docs.mongodb.com/master/release-notes/7.0-compatibility/#feature-compatibility. :: caused by :: Invalid feature compatibility version value '6.0'; expected '7.0' or '7.3' or '8.0'. See https://docs.mongodb.com/master/release-notes/7.0-compatibility/#feature-compatibility.). If the current featureCompatibilityVersion is below 7.0, see the documentation on upgrading at https://docs.mongodb.com/master/release-notes/7.0/#upgrade-procedures."}}

A few lines later the log ends with "msg":"Shutting down","attr":{"exitCode":62}.

The check runs when mongod reads the FCV document at startup. In MongoDB 8.0.38, feature_compatibility_version.cpp turns any FCV it cannot parse into a MustDowngrade error:

if (!swVersion.isOK()) {
    uassertStatusOK({ErrorCodes::MustDowngrade,
                     str::stream()
                         << "UPGRADE PROBLEM: Found an invalid featureCompatibilityVersion "
                            "document (ERROR: "
                         << swVersion.getStatus()
                         << "). If the current featureCompatibilityVersion is below "
                         << multiversion::toString(multiversion::GenericFCV::kLastLTS)
                         ...

The accepted list comes from feature_compatibility_version_parser.cpp: the last LTS, the last continuous (rapid) release, and the server’s own version. For 8.0 that is '7.0' or '7.3' or '8.0'. mongod_main.cpp catches MustDowngrade, logs "Wrong mongod version", and exits with ExitCode::needDowngrade, which exit_code.h defines as 62 with the comment “This exe can’t use the existing data files”. All links are to the r8.0.38 tag (commit 11d6674).

MongoDB 9.0.8 prints the list in a different format, including a doubled quote: Expected one of the following versions: ''9.0', '8.3', '8.0'. That is in the source too. At r9.0.8 (parser, commit ace0d09) the message adds a ' and then each version adds its own quotes.

Pulled from Docker Hub on 26 November 2026 (linux/amd64). Versions are the image’s MONGO_VERSION. The FCV column is what a fresh volume reported with db.adminCommand({getParameter:1, featureCompatibilityVersion:1}). The tag list matches library/mongo in docker-library/official-images.

Reproduced: which jumps work

Each volume was written by one tag (one insert, then docker stop) and then mounted at /data/db by another tag. That is the layout of a Compose service with volumes: - mongo-data:/data/db. Docker Compose itself was not installed on the test machine, so the containers were started with docker run and named volumes. No authentication, standalone mongod, default settings.

Three patterns show up. Skipping a major fails (6.0 → 8.0, 7.0 → 9.0). Going backwards fails, even inside one major (8.3 → 8.0). And the error text depends on the new server, so the same 6.0 volume gives a different message under 8.0 and 9.0.

A failed start does not damage the data. After both 8.0 and 9.0 refused the 6.0 volume, mongo:7.0 started on it, reported FCV 6.0, and the upgrade below finished with the test document intact.

Why CI stays green while local Compose breaks

GitHub’s service container docs say: “GitHub creates a fresh Docker container for each service configured in the workflow, and destroys the service container when the job completes.” A mongo service in CI starts with an empty /data/db, so any tag starts. The error shows up on a developer machine whose Compose volume was written by a different MongoDB. Typical ways to get there:

  • Compose had mongo:6 or mongo:7, CI moved to mongo:8 or latest, and someone changes Compose to “match CI.”
  • Compose used mongo:latest or mongo:8, which moved to 9.0.8 or 8.3.17. Someone then pins Compose to mongo:8.0 to match the workflow, and the volume is now too new.
  • A data directory or volume copied from a newer server is used by an older test container.

Fix it: upgrade one step at a time

MongoDB’s Upgrade a Standalone to 8.0 page (read 26 November 2026) says: “To upgrade from a version earlier than the 7.0-series, you must successively upgrade major releases until you have upgraded to 7.0-series. For example, if you are running a 6.0-series, you must upgrade first to 7.0 before you can upgrade to 8.0.” It also requires FCV "7.0" before moving to 8.0. The setFeatureCompatibilityVersion reference says the confirm field is “New in version 7.0” and that without confirm: true “the command fails and returns a warning about modifying the feature compatibility version.”

This is the real run that took the 6.0 volume to 9.0. Between steps, the container was stopped and started again on the same volume with the next tag (in Compose: change the tag, then docker compose up -d, then docker compose exec db mongosh):

# mongo:7.0 on the 6.0 volume
$ mongosh --eval 'db.version()'
7.0.48
$ mongosh --eval 'db.adminCommand({getParameter:1,featureCompatibilityVersion:1})'
{ featureCompatibilityVersion: { version: '6.0' }, ok: 1 }
$ mongosh --eval 'db.adminCommand({setFeatureCompatibilityVersion:"7.0"})'
MongoServerError: Once you have upgraded to 7.0, you will not be able to downgrade FCV and binary version without support assistance. Please re-run this command with 'confirm: true' to acknowledge this and continue with the FCV upgrade.
$ mongosh --eval 'db.adminCommand({setFeatureCompatibilityVersion:"7.0", confirm:true})'
{ ok: 1 }

# mongo:8.0 on the same volume
$ mongosh --eval 'db.version()'
8.0.38
$ mongosh --eval 'db.adminCommand({getParameter:1,featureCompatibilityVersion:1})'
{ featureCompatibilityVersion: { version: '7.0' }, ok: 1 }
$ mongosh --eval 'db.adminCommand({setFeatureCompatibilityVersion:"8.0", confirm:true})'
{ ok: 1 }
$ mongosh --eval 'db.getSiblingDB("app").orders.findOne({},{_id:0})'
{ n: 42 }

# mongo:latest (9.0.8) on the same volume
$ mongosh --eval 'db.version()'
9.0.8
$ mongosh --eval 'db.adminCommand({setFeatureCompatibilityVersion:"9.0", confirm:true})'
{ ok: 1 }
$ mongosh --eval 'db.adminCommand({getParameter:1,featureCompatibilityVersion:1})'
{ featureCompatibilityVersion: { version: '9.0' }, ok: 1 }
$ mongosh --eval 'db.getSiblingDB("app").orders.findOne({},{_id:0})'
{ n: 42 }

The confirm message is in set_feature_compatibility_version_command.cpp at r8.0.38. 8.0 → 9.0 and 8.3 → 9.0 started directly in the test, so from 8.0 you do not need to stop at 8.3. If your database uses authentication, add your usual -u/-p options. Only the no-auth case was tested here.

  1. Back up first. mongodump --archive=backup.gz --gzip worked from inside the container (mongodump and mongorestore 100.20.1 ship in the 9.0.8 and 7.0.48 images).
  2. Find the FCV on disk. Start the tag that wrote the volume, or read it from the error line: version: "6.0" in the message above.
  3. Step one major at a time (6.0 → 7.0 → 8.0 → 9.0). After each start, run setFeatureCompatibilityVersion with confirm: true, then move to the next tag.
  4. Then change the pin everywhere (Compose, workflow services:, Testcontainers, .env.example) in one pull request.

Going back to an older tag

The FCV can be lowered while the newer server is running. Lowering it on 8.0 without confirm printed:

MongoServerError: Once you have downgraded the FCV, if you choose to downgrade the binary version, it will require support assistance. Please re-run this command with 'confirm: true' to acknowledge this and continue with the FCV downgrade.

With confirm: true, an 8.0 volume set to FCV "7.0" then started under mongo:7.0 and returned the document. The same worked for 9.0 → FCV 8.0 → mongo:8.0, and for 8.3 → FCV 8.0 → mongo:8.0. That was a one-document standalone test. The server message above says a binary downgrade “will require support assistance,” and the 8.0 upgrade page says “MongoDB only supports single-version downgrades.” For local or CI data, two simpler options:

  • Dump and restore into the older version. A mongodump --archive --gzip from 9.0.8 restored into a fresh mongo:7.0 volume with mongorestore: 1 document(s) restored successfully. 0 document(s) failed to restore.
  • Reset the volume if the data is throwaway. docker compose down -v removes “named volumes declared in the ‘volumes’ section of the Compose file and anonymous volumes attached to containers” (compose down reference). This deletes the data.

Pin one version everywhere

Because mongo:8 is 8.3 today and 8.0 cannot open 8.3 data, pin the minor (mongo:8.0), not just the major. Use the same value in every file:

# .env.example
MONGO_VERSION=8.0

# docker-compose.yml
services:
  db:
    image: mongo:${MONGO_VERSION:-8.0}
    volumes:
      - mongo-data:/data/db
volumes:
  mongo-data:

# .github/workflows/ci.yml
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      mongo:
        image: mongo:8.0.38
        ports:
          - 27017:27017
        options: >-
          --health-cmd "mongosh --quiet --eval 'db.runCommand({ping:1}).ok'"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

That --health-cmd reported healthy (exit 0, output 1) on mongo:8.0.38 with docker run. It was not run on a GitHub-hosted runner for this guide.

What ServiceGate does not detect

  • Minor drift does not fail the job. ServiceGate 0.1.0 reports 8.3 vs 8.0 as a warning (exit 0). For MongoDB that is not enough: 8.0 cannot open 8.3 data, as reproduced above. Read the warnings, or gate on --json output yourself.
  • A floating major is not compared with a minor. Compose mongo:8 and workflow mongo:8.0 produced no drift finding (exit 0, only the health-check warning) in both the CLI and Lite. Today mongo:8 is 8.3.17.
  • It does not know MongoDB’s upgrade path. It reports that pins disagree. It does not say that 6.0 → 8.0 needs a stop at 7.0, or that a change of pin needs setFeatureCompatibilityVersion.
  • It does not look at volumes or the FCV. It reads tags in committed files. It cannot see which MongoDB wrote a developer’s volume, so it cannot predict this error on a given machine. If every file is changed from mongo:6.0 to mongo:8.0 together, ServiceGate passes and old local volumes still fail.
  • It does not resolve tags. It flags latest and a missing tag as unpinned. It does not know that latest means 9.0.8 today.
  • Replica sets and sharded clusters were not tested. Everything here is a single standalone mongod without authentication.
