pg_dump failed because the client and the service were different majors

Upgrading the Postgres service in CI is not enough if the client tools on the runner, or in another file, stay on an older major.

Cal.com fixed a related failure on 4 March 2026: CI had been upgraded to PostgreSQL 18, and the runner’s host pg_dump (v16) refused to dump the server. The fix ran pg_dump / psql inside postgres:18 so the client and server versions match. See calcom/cal.diy commit 3f2e122 (fix: use docker postgres:18 for pg_dump/psql to fix version mismatch (#28260)).

Shallow Brook Software documented the same class of failure after unpinning Postgres in a Compose file: pg_dump: error: server version: 16.2 …; pg_dump version: 14.11 / aborting because of server version mismatch. The write-up is Using Newer PostgreSQL Client Tools in GitHub Actions.

The Stack Overflow question GitHub Actions: Use same version of psql and PostgreSQL service describes a service container on postgres:17 with Ubuntu-runner client tools on 14.13. It has a score of 2 and 456 views (Stack Exchange API, 10 November 2026).

Pin the service, wait until it is ready, and keep the client in step

Official GitHub docs for Creating PostgreSQL service containers (fetched 10 November 2026) require a service image and include --health-cmd pg_isready so the job waits until Postgres is ready. The documented example uses the untagged postgres image (implicit latest), which is the unpinned-tag case a consistency check can warn about. Pair a numeric major tag with a health check, and if you call pg_dump or psql, run a client from the same major — in the service image, or from a matching image — rather than assuming the runner’s host tools will match.

The free ServiceGate Lite Action compares Compose files to GitHub Actions service images and warns when a known-family service has no --health-cmd or when a tag is unpinned. It does not inspect pg_dump itself. The full CLI covers the same warnings, plus Dockerfiles and Testcontainers literals. Checkout is not live.
