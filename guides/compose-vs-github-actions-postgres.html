Do your Compose file and GitHub Actions agree on Postgres?

A Compose image: line and a workflow services: image are two declarations. They drift unless something compares them.

Local development often starts Postgres from a Compose file. CI often starts it as a GitHub Actions service container. Those two files are usually edited in different pull requests. The result can be a green CI job on one major and a laptop or deploy on another.

That split is documented. On 10 November 2026, a scan of graphile/worker at commit b4f1b41c7abd747586879bf68a46a5a22897fa96 found postgres:12-alpine in docker-compose.yml and postgres:14 on two jobs in .github/workflows/ci.yml. The same workflow also tests a matrix of majors 14 through 18, so 12 is not in the set CI actually runs. This write-up does not claim the project uses ServiceGate; it is a public tree that shows the file-to-file disagreement.

The other direction is also documented: bump both files in the same change. blockscout/blockscout #11334 (merged 9 December 2024) updated Docker Compose and GitHub Actions workflows together when moving Postgres 15 to 17.

A later pattern is a shared variable. cibrandocampo/nudge commit 01c8fb1 (1 May 2026) bumped postgres:16-alpine to postgres:17-alpine and redis:7-alpine to redis:8-alpine in CI services and in dev/prod Compose defaults, via shared DOCKER_POSTGRES_VERSION / DOCKER_REDIS_VERSION variables, so a single env edit keeps both stacks in sync. A scan of that repository at bb3b462f35d0f37ee06180d06c3050c969b5b017 (9 November 2026) still had those pins in agreement.

Compare the two pins in CI

Official GitHub docs for Creating PostgreSQL service containers (fetched 10 November 2026) require a service image and include --health-cmd pg_isready so the job waits until Postgres is ready. They do not compare that image to a Compose file. A small scan of both sources catches the 12-vs-14 class of drift before a review has to notice it by eye.

The free ServiceGate Lite Action compares Compose files to GitHub Actions services: and fails the job when known families disagree on the major. A missing --health-cmd on a known-family service is a warning, not a failure. The full CLI also reads Dockerfiles, Testcontainers literals, and committed .env.example version variables.
