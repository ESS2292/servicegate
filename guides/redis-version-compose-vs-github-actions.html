Redis version drift between docker-compose.yml and GitHub Actions services

A Compose file that says redis:7-alpine and a workflow service that says redis, redis:latest, or redis:6.2 are not running the same server. Code that works on one can fail on the other.

What the tags point to today

Floating Docker tags move. According to the Redis entry in docker-library/official-images on 15 November 2026:

TagResolves to
redis, redis:latest, redis:88.10.3
redis:7, redis:7.47.4.12
redis:7.27.2.17
redis:6, redis:6.26.2.24

So redis:7 in Compose next to redis:latest in CI is 7.4 on a laptop and 8.10 in CI, and the gap changes whenever a new 8.x lands. The official GitHub docs example for Creating Redis service containers (fetched 15 November 2026) uses image: redis with no tag, which means latest. Copying that example into a workflow is a common way to end up with an unpinned CI Redis.

Differences that actually break things

The clearest failures are commands that do not exist on the older server. Per the “Available since” line on each official Redis command page (checked 15 November 2026):

  • Redis 6.2.0: GETDEL and GETEX.
  • Redis 7.0.0: LMPOP, FUNCTION LOAD (Redis Functions), and sharded pub/sub SPUBLISH. The EXPIRE options NX, XX, GT, and LT were also added in 7.0.0.
  • Redis 7.4.0: HEXPIRE (per-field expiration on hashes).

If local development runs redis:7.4 and CI runs redis:6.2, a feature that uses HEXPIRE or EXPIRE key 60 NX works on the laptop and returns an error from the server in CI. Reverse the drift (newer in CI, older in Compose or production) and CI passes on code that the older server rejects.

Persistence is the other one-way door. The Redis 7.0 release notes say Redis 7 “uses a new version 10 format for RDB files, which is incompatible with older versions,” and that Redis 7 stores AOF as multiple files in a folder. If a Compose named volume holds an RDB file written by a 7.x container, a 6.2 container cannot load it. Moving a dev volume back to an older major is not a tag change; it is a data reset. CI service containers are usually throwaway, so this mostly bites the Compose side.

If you are moving between Redis and Valkey, treat that as a separate migration with its own release notes. This guide does not compare the two.

Pin, and keep one source of truth

  1. Pick a granularity on purpose. redis:7.4-alpine pins major and minor and still takes patch releases. redis:7-alpine follows the latest 7.x. redis / redis:latest follows whatever the newest release is.
  2. Use the same tag in both files. The Compose service and the workflow service should carry the identical string, or one should be derived from the other.
  3. Keep the health check. GitHub’s example adds --health-cmd "redis-cli ping" so the job waits until Redis answers.
  4. Upgrade both in one pull request and read the release notes for every major you cross.
# docker-compose.yml
services:
  redis:
    image: redis:7.4-alpine

# .github/workflows/ci.yml
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      redis:
        image: redis:7.4-alpine
        ports:
          - 6379:6379
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

Two files with one string is still two declarations. The point of a check is to fail the pull request that changes only one of them.

How ServiceGate catches this

Behavior below was confirmed by running the ServiceGate 0.1.0 CLI and the Lite Action’s scanner against small test repositories on 15 November 2026:

  • Major drift (error). Compose redis:7.4-alpine vs workflow service redis:6.2-alpine fails with Redis major versions disagree: 7.4 (docker-compose.yml:3, compose redis); 6.2 (.github/workflows/ci.yml:8, workflow redis). A Compose default such as redis:${REDIS_VERSION:-7.4}-alpine is resolved and compared the same way.
  • Minor drift (warning). redis:7.2 vs redis:7.4 is reported as a minor/patch disagreement. It does not fail the job, even though 7.4 added HEXPIRE.
  • Unpinned image (warning; error with --strict-pins in the CLI). redis, redis:latest, or a non-version tag like alpine. Because latest has no version to compare, redis:7 vs redis:latest is this warning, not a drift error.
  • Missing health check (warning). A Redis service in GitHub Actions with no --health-cmd.

The Redis family includes redis, bitnami/redis, redis/redis-stack, redis/redis-stack-server, cimg/redis, and circleci/redis. Valkey images are a separate family and are not compared to Redis. A workflow image written as an expression, such as ${{ vars.REDIS_IMAGE }}, is skipped. ServiceGate compares tags in your files; it does not pull images, resolve what latest points to, or test command compatibility.
