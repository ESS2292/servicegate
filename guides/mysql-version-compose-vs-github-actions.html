MySQL version drift between docker-compose.yml and GitHub Actions services

A Compose file that says mysql:8.0 and a workflow service that says mysql:8.4, mysql:9.7, or mysql:latest are not running the same server. Since MySQL 8.4, that gap includes a server option that no longer exists and an authentication plugin that is off by default.

What the tags point to today

Floating Docker tags move. According to the official mysql image on Docker Hub (tag digests compared through the Docker Hub API on 20 November 2026):

TagResolves to
mysql, mysql:latest, mysql:innovation, mysql:2626.10.0
mysql:lts, mysql:9, mysql:9.79.7.4
mysql:8, mysql:8.48.4.13
mysql:8.08.0.46 (last updated 5 May 2026)

Two things in that table surprise people. First, mysql:8 is 8.4, not 8.0, so “we’re on 8” can mean either series depending on which file you read. Second, latest follows the Innovation track, not the long-term-support track: it is a different server from mysql:lts. The MySQL 8.0 release notes say 8.0 reached end of life in April 2026 with 8.0.46, and Oracle’s EOL notice points 8.0 users to 8.4 LTS or 9.7 LTS. A Compose file still on mysql:8.0 next to a CI service someone already moved forward is a common shape for this drift.

Differences that actually break things

  • A removed server option stops the container. Many 8.0-era Compose files pass --default-authentication-plugin=mysql_native_password. That option was removed in 8.4. In docker-library/mysql issue #1048, a maintainer shows mysql:8.4.0 exiting with [ERROR] [MY-000067] [Server] unknown variable 'default-authentication-plugin=mysql_native_password'. followed by [ERROR] [MY-010119] [Server] Aborting. The same command: line works on mysql:8.0.
  • mysql_native_password is off by default in 8.4 and gone in 9.0. The MySQL 8.4 manual page on Native Pluggable Authentication says the plugin is “deprecated as of MySQL 8.0.34, disabled by default in MySQL 8.4, and removed as of MySQL 9.0.0.” On 8.4, creating or altering a user with it fails with ERROR 1524 (HY000): Plugin 'mysql_native_password' is not loaded, and existing accounts that use it cannot log in. It can be re-enabled on 8.4 with --mysql-native-password=ON; on 9.x and later there is no plugin to enable. A CI init script that creates a native-password user passes on mysql:8.0 and fails on mysql:8.4 or mysql:latest.
  • A Compose volume does not go backwards. The MySQL 8.4 downgrade chapter lists in-place downgrade only within an LTS series. Going from 8.4 to 8.0 is supported only by logical dump and load or replication, and only for rollback. If a named volume was opened once by an 8.4 or newer container, switching that Compose service back to mysql:8.0 is a data reset or a dump and restore, not a tag edit. CI service containers are usually throwaway, so this mostly bites the Compose side.

Those are the breaks with exact, documented error text. The What Is New in MySQL 8.4 since MySQL 8.0 page lists more changes (InnoDB defaults, removed options, removed keywords). Read it, and the release notes for every series you cross, before moving either file.

Pin, and keep one source of truth

  1. Pick a series on purpose. mysql:8.4 or mysql:9.7 stays on an LTS series and still takes patch releases. mysql:latest follows Innovation releases, which MySQL supports only until the next one.
  2. Use the same tag everywhere it is declared. Compose, the workflow services: block, any database Dockerfile, and the MYSQL_VERSION in .env.example should say the same thing.
  3. Drop removed options when you move to 8.4. Delete --default-authentication-plugin; if you still need native passwords for a while, use --mysql-native-password=ON on 8.4 and plan the move to caching_sha2_password before 9.x.
  4. Upgrade every file in one pull request.
# .env.example
MYSQL_VERSION=8.4

# docker-compose.yml
services:
  db:
    image: mysql:${MYSQL_VERSION:-8.4}

# docker/db/Dockerfile
FROM mysql:8.4

# .github/workflows/ci.yml
jobs:
  test:
    runs-on: ubuntu-latest
    services:
      mysql:
        image: mysql:8.4
        env:
          MYSQL_ROOT_PASSWORD: root
          MYSQL_DATABASE: app
        ports:
          - 3306:3306
        options: >-
          --health-cmd "mysqladmin ping -h 127.0.0.1"
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

Four files with one string is still four declarations. The point of a check is to fail the pull request that changes only one of them.

How ServiceGate catches this

The output below is copied from the ServiceGate 0.1.0 CLI (servicegate check), run against small test repositories on 20 November 2026.

Major drift fails the job. .env.example sets MYSQL_VERSION=8.4, Compose uses mysql:${MYSQL_VERSION}, the workflow service is mysql:9.7, and a database Dockerfile still says FROM mysql:8.0. Exit code 1:

ServiceGate checked 4 service image pins across 1 service family.

Errors (1):
  [version-drift] MySQL major versions disagree: 8.4 (docker-compose.yml:3, compose db); 9.7 (.github/workflows/ci.yml:8, workflow mysql); 8.0 (docker/db/Dockerfile:1, dockerfile); 8.4 (.env.example:1, MYSQL_VERSION).

8.0 vs 8.4 is a warning, not a failure. Compose mysql:8.0 and workflow service mysql:8.4. Exit code 0:

ServiceGate checked 2 service image pins across 1 service family.

Warnings (1):
  [minor-drift] MySQL 8 pins disagree on minor/patch: 8.0 (docker-compose.yml:3, compose db); 8.4 (.github/workflows/ci.yml:8, workflow mysql).

To be clear about this limit: ServiceGate fails on a different leading version number. For MySQL, 8.0 and 8.4 share a leading 8 even though the authentication change above landed between them, so this case is reported but does not fail CI. Treat this warning as a real problem for MySQL.

Unpinned images are warnings (errors with --strict-pins). mysql in Compose and mysql:latest in CI. Exit code 0 by default, 1 with --strict-pins:

ServiceGate checked 2 service image pins across 1 service family.

Warnings (2):
  [unpinned-image] MySQL image is unpinned (latest) at docker-compose.yml:3 (compose). Pin a numeric major tag instead of 'latest'.
  [unpinned-image] MySQL image is unpinned (latest) at .github/workflows/ci.yml:8 (workflow). Pin a numeric major tag instead of 'latest'.

After the fix above (all four declarations on 8.4). Exit code 0:

ServiceGate checked 4 service image pins across 1 service family.
OK — Compose, CI, and test service images agree.

The MySQL family includes mysql, bitnami/mysql, mysql/mysql-server, cimg/mysql, and circleci/mysql. MariaDB images are a separate family and are not compared to MySQL. ServiceGate compares tags in your files; it does not pull images, resolve what latest points to, read command: flags, or test authentication.
